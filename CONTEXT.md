# Project: PremiumCoffee — Premium Coffee Shop (Backend + Catalog + 3D Builder)

## Goal

Build a premium coffee shop web application as a professional learning project, focused primarily on Kotlin backend development, clean architecture, PostgreSQL, Docker, CI/CD, and a catalog with variants that can be visualized in 3D.

The user wants to learn while building the project, so the entire application must not be generated at once. Implement it step by step and explain the important decisions.

---

# Stack (currently in use)

## Backend

* Kotlin 2.3.10
* Spring Boot 4.1.1
* Java 21 (toolchain)
* Gradle 9 (Kotlin DSL, wrapper)
* Spring Data JPA (Hibernate 7) — **decision**: use JPA instead of Spring Data JDBC to use entities with `ddl-auto=validate` against the schema
* PostgreSQL → **hosted on Supabase** (not local PostgreSQL)
* Flyway (owns the schema and versioned migrations)
* REST API
* Docker / Docker Compose

Database decision: the direct Supabase host (`db.<ref>.supabase.co`) only supports IPv6, not IPv4, so it cannot connect from Windows/Docker. Use the **pooler** `aws-0-us-east-2.pooler.supabase.com` with the `postgres.<project_ref>` user. Real credentials are stored in the gitignored `.env` file. The `db-migration` service/direct connection is not kept in the repository.

## Future backend

* Clean Architecture (`domain / application / infrastructure` modules)
* Ports and adapters: the domain must not depend on Spring, PostgreSQL, MinIO, or Cloudinary
* Spring Data JDBC was discarded in favor of JPA

## Future frontend

* Next.js + React + Three.js
* SSR for initial product and variant information
* Three.js/WebGL for the interactive 3D viewer

## Future storage

Development:
* MinIO through Docker (S3 compatible)

Production/future:
* Cloudinary initially as a storage/CDN option
* S3/R2 as a future possibility

# Current project status

## Infrastructure

* Dockerized Spring Boot application: multi-stage `Dockerfile` (Gradle build → JRE image) and `docker-compose.yml` with only the `app` service (it does not include PostgreSQL)
* `.dockerignore` excludes `.env`; the container receives `DB_URL`, `DB_USER`, and `DB_PASSWORD` through environment variables
* `application.properties` reads the three environment variables and sets `spring.datasource.hikari.maximum-pool-size=10`, `spring.jpa.hibernate.ddl-auto=validate`, and `spring.jpa.open-in-view=false`
* Root package: `Coffee` (not `com.xxx`)

## Entities (7) and enums — `src/main/kotlin/Coffee/<Entity>/`

* `Category` (hierarchy with a self-referencing `parent`)
* `Product` (must have a `category`)
* `ProductVariant` (must have a `product`)
* `ProductVariantPrice` (`BigDecimal` price, `validFrom`, `validUntil`, `currency` = `COP`)
* `MediaAsset` (file metadata)
* `ProductVariantMedia` (variant ↔ asset relationship with a `role`)
* `Variant3DComponent` (3D components for the future Builder)

Enums: `MediaAssetType` (IMAGE, SVG, MODEL_3D), `MediaProvider` (MINIO, CLOUDINARY, S3), and `VariantMediaRole` (PRIMARY, GALLERY, THUMBNAIL, POSTER, MODEL_3D).

Entity conventions: UUIDs generated by the application (`UUID.randomUUID()`), `Instant` dates, `BigDecimal` prices, and enums mapped with `@Enumerated(EnumType.STRING)`.

## Business layers (organized by aggregate)

Each aggregate groups its layers in its own package (`Coffee.<Entity>.<Layer>`):

```
Coffee/
├── Category/
│   ├── Controller/  → CategoryController.kt
│   ├── DTO/         → CategoryRequest.kt, CategoryResponse.kt
│   ├── Model/       → Category.kt
│   ├── Repository/  → CategoryRepository.kt
│   └── Services/    → CategoryService.kt
├── Product/  ────────────────── (same structure)
├── ProductVariant/  ─────────── (same structure)
├── ProductVariantPrice/  ────── (same structure)
├── MediaAsset/  ─────────────── (same structure)
├── ProductVariantMedia/  ────── (same structure)
├── Variant3DComponent/  ─────── (same structure)
└── Common/
    ├── Controllers/  → shared CRUD controller and API exception handler
    ├── DTO/          → PageResponse.kt
    ├── Exceptions/   → ResourceNotFoundException.kt
    ├── Models/       → PageQuery.kt, PageResult.kt
    ├── Ports/        → CrudRepositoryPort.kt
    └── Services/     → shared CRUD service
```

Classes from related aggregates are imported across packages when necessary (for example, `Product.Model` imports `Category.Model.Category`). Each aggregate keeps its enums in its `Model` package (`MediaAssetType` and `MediaProvider` in MediaAsset, `VariantMediaRole` in ProductVariantMedia).

Every layer follows the English convention: `findAll(query)`, `findById(id)`, `create(request)`, `update(id, request)`, and `delete(id)`.

* REST endpoints for each aggregate: `GET /resource`, `GET /resource/{id}`, `POST /resource` (201), `PUT /resource/{id}`, and `DELETE /resource/{id}` (204)
* Routes: `/categories`, `/products`, `/product-variants`, `/product-variant-prices`, `/media-assets`, `/product-variant-media`, and `/variant-3d-components`
* List responses are paginated with `page` (default `0`), `size` (default `20`, maximum `100`) and ascending ID order; the body contains `content`, `page`, `size`, `totalElements`, and `totalPages`
* Controllers and services use dedicated request/response DTOs; JPA entities are never exposed directly by REST responses
* Request DTOs use Bean Validation; invalid fields return 400, missing resources return 404, and unique-constraint or referenced-row conflicts return 409 using `ProblemDetail`
* Service reads use read-only transactions and writes use write transactions; relationships are LAZY and `open-in-view=false`
* Services resolve parent references before writes; missing references return 400, while missing resources return 404
* Deletes do not cascade. A foreign-key violation is returned as 409 so the client can remove dependent records explicitly before retrying

## Applied migrations — `src/main/resources/db/migration/`

| Migration | Purpose |
|---|---|
| `V1__crear_tabla_cafe.sql` | Creates the test `cafe` table (leftover, pending removal in `V4`) |
| `V2__crear_tablas_catalogo.sql` | Creates all seven catalog tables in one migration |
| `V3__ajustar_currency_a_varchar.sql` | Changes `currency` from `CHAR(3)` to `VARCHAR(3)` (detected by `validate`: bpchar ≠ varchar) |

The historical migration filenames remain unchanged because those migrations have already been applied.

Rule: **never modify an applied migration** because Flyway reports a checksum error. Put every subsequent change in a new migration.

# Database

Main tables (catalog — already created):

categories · products · product_variants · product_variant_prices · media_assets · product_variant_media · variant_3d_components

The V2 catalog schema is authoritative: UUIDs, unique `slug`, `created_at`/`updated_at`, `currency VARCHAR(3)` after V3, and `price NUMERIC(12,2)` — never use FLOAT for money.

order_items:
* id UUID, order_id FK, variant_id FK, product_name, variant_name, quantity, unit_price, subtotal

# Multimedia system (future)

Do not store large files in PostgreSQL: the database stores metadata and relationships, while MinIO or Cloudinary stores the files.

The `media_assets` table already exists with: asset_type, provider, storage_key, public_id, url, mime_type, file_name, file_size_bytes, width, and height.

asset_type: IMAGE, SVG, MODEL_3D · provider: MINIO, CLOUDINARY, S3.

Variant media (`product_variant_media`) already exists with: variant_id, media_asset_id, role, sort_order, and is_primary.

A variant can have standard images, SVG, a poster, and a GLB model.

# 3D models (future)

* Main format: GLB. Do not use SVG as a substitute for a 3D model.
* SVG can exist as an asset and later be used for geometric or procedural generation.
* GLB files can represent either a complete variant model or independent 3D components for the Builder.

Example structure:
```
variants/{variantId}/
├── base.glb
├── poster.webp
├── thumbnail.webp
└── components/
    ├── cream.glb
    ├── chocolate.glb
    ├── oreo.glb
    └── caramel.glb
```

Chocolate Milkshake example: Glass, Liquid, Cream, ChocolateSauce, and OreoTopping allow components to be enabled or disabled in a 3D Builder.

The `variant_3d_components` table already exists with: id, variant_id, name, code, media_asset_id, required, and default_enabled.

# 3D viewer (future)

Three.js handles GLB loading, rotation, zoom, camera, lighting, materials, components, and interaction.

The Kotlin backend does not render the 3D content. It manages variants and assets, validates options, returns URLs, and handles business rules.

SSR with Next.js does not render the 3D content. It delivers the name, description, price, variant information, poster, and SEO metadata; the browser then initializes Three.js and loads the GLB.

# GLB generation (future, independent, and deferred)

* Explore free or local 3D model generation (open source: Hunyuan3D, TripoSR, or other options).
* Independent service, possibly requiring a GPU, with asynchronous jobs:
  `POST /api/v1/generations` → `{ jobId, status: "PROCESSING" }`, followed by `GET /api/v1/generations/{jobId}`.
* Flow: Image → 3D Generation Service → Mesh → Texture → Optimization → GLB → MinIO/Cloudinary → `media_assets`.
* Future possibility: procedural generation (SVG/profile → Extrude/Revolve → Mesh → GLB) for cups, glasses, and containers. Do not implement it yet.

# Caching and optimization (future/incremental)

* Browser cache, CDN, HTTP caching, lazy loading, thumbnails, posters, optimized GLB files, compression, WebP/AVIF, and versioned immutable URLs.
* Immutable assets: `Cache-Control: public, max-age=31536000, immutable`.
* Do not publicly cache private order or customer information.
* Do not introduce Redis at the beginning: measure first.

# Future architecture

Backend organized into Clean Architecture modules:

```
catalog/   domain/ application/ infrastructure/
order/     domain/ application/ infrastructure/
media/     domain/ application/ infrastructure/
3d-generation/ domain/ application/ infrastructure/
```

The domain must not depend on Spring, PostgreSQL, MinIO, or Cloudinary. Use ports and adapters; for example, define `MediaStorage` in Domain/Application and `MinioMediaStorage`/`CloudinaryMediaStorage` in Infrastructure.

Current note: the project still uses an aggregate-oriented structure, with each entity containing `Model/DTO/Repository/Services/Controller`. Moving to domain modules with `domain/application/infrastructure` is a future step when the project grows.

# Important principles

1. Do not overengineer from the beginning.
2. Implement vertical slices.
3. Start with the basic catalog (done).
4. Add media next.
5. Add the GLB viewer.
6. Add the Builder.
7. Add 3D generation.
8. Add advanced optimization.
9. Explain technical decisions before implementing them.
10. Prioritize maintainable, understandable code over unnecessary complexity.

# OpenCode rule

Do not generate the entire application automatically.

Work step by step with the user. Before creating an important piece:
1. explain what will be done;
2. explain why;
3. show the structure;
4. implement it;
5. review it;
6. run the tests;
7. continue with the next step.

If an important architectural decision is required, stop and explain it before implementation.

The goal is not only to have a working application; it is to learn how to build a professional Kotlin backend with clean architecture, asset storage, and an interactive 3D experience.
